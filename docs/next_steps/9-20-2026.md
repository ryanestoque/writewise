## The Critical Path (in order)

Everything below is sequential — each step depends on the one before it. This is the chain that ends with a working, defense-ready system.

### 1. Collect Enough Paired Data 🔴 IN PROGRESS

**What:** Teachers using the live Phase 1 system to upload real student worksheets *and* enter their manual rubric scores (the 4-band rating: Needs Improvement / Developing / Satisfactory / Excellent) for all five criteria per submission.

**Why it matters:** Every single step below feeds off this data. No paired data → no calibration → no auto-scoring → no defense.

**What "enough" means:**
- For Spearman's Rho (ρ ≥ 0.70 target): ~16 paired observations per criterion is technically sufficient, but you want more for confidence
- For threshold derivation: you need reasonable coverage across all 4 bands — if 90% of scores cluster in "Satisfactory," your threshold boundaries at the extremes (Excellent / Needs Improvement) will be shaky
- For CNN Stage 2 training: 150 submissions × multiple word crops = ~500–1,500 word-level training samples. That's thin for deep learning, which is why the architecture freezes the backbone and only trains a tiny regression head
- **~150 scored submissions is workable** ([previous conversation](file:///C:/Users/Admin/.gemini/antigravity-ide/brain/e3550f39-1866-4d24-8343-fadab95233f5/.system_generated/logs/transcript.jsonl)), but you want band distribution to be as even as realistically possible

> [!WARNING]
> If Phase 1 data collection slips past late September, the entire calibration → integration → evaluation chain has almost zero slack left before the October defense. Track this **weekly** — count scored submissions, check band distribution.

### 6. Build the `ScoreProvider` Abstraction 🟢 DONE

**What:** Implement the `ManualScoreProvider` / `CalibratedScoreProvider` interface described in [ARCHITECTURE.md §10](file:///c:/Users/Admin/Documents/CODING PROJECTS/writewise/docs/ARCHITECTURE.md).

**Status:** Built in [`backend/app/scoring/provider.py`](file:///c:/Users/Admin/Documents/CODING PROJECTS/writewise/backend/app/scoring/provider.py) with full test suite (`backend/tests/scoring/test_provider.py`). Integrated into the `create_submission` endpoint in [`backend/app/api/submissions.py`](file:///c:/Users/Admin/Documents/CODING PROJECTS/writewise/backend/app/api/submissions.py).

**How it works:**
- `ManualScoreProvider` (Phase 1, active default): returns `None` for all score columns at upload time; teachers enter rubric scores later via `PATCH /api/submissions/{id}/manual-score`
- `CalibratedScoreProvider` (Phase 2, ready): applies threshold formulas to raw CV measurements for the 4 OpenCV criteria; identity passthrough for letter formation (CNN output is already calibrated)
- Switched via `SCORING_ENGINE=manual|calibrated` config flag
- API response shape stays identical regardless of which provider runs — frontend never knows the difference
- Populates the 5 score columns in the `measurement` table when calibrated mode is active (Postgres computes generated `composite_score`)

**Doc pointers:** [ARCHITECTURE.md §10](file:///c:/Users/Admin/Documents/CODING PROJECTS/writewise/docs/ARCHITECTURE.md), [ML_PIPELINE §6.5](file:///c:/Users/Admin/Documents/CODING PROJECTS/writewise/docs/ML_PIPELINE.md)
